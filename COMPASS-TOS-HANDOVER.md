## 1. Executive Summary

**What this project is:**
COMPASS-TOS ("Travel Operating System") is a custom-built, self-hosted, browser-based trip-planning web application. It started life as a static single-trip HTML template ("La Grande Italia 2027 — The Henderson Grand Tour") and was rebuilt from the ground up into a full multi-trip, multi-user, persistent web application with a real Node.js backend. The codebase is **plain vanilla JavaScript, HTML, and CSS — deliberately no frameworks** (no React/Vue/Express/etc.), per the project's own stated design principles (see Section 2).

**Current overall objective:**
Build a fully-featured, multi-user, family-shared trip planner that the user (Mick Henderson) and his family can use to plan and later travel with. It needs to support: researching and booking Accommodation, Activities, Transport, Restaurants, and Flights; tracking a Budget and day-to-day Expenses; keeping a photo-and-notes Journal (exportable at trip's end); and doing all of this from both desktop and mobile, with real persistence, for multiple trips, with multiple family members each having their own login.

**What has already been accomplished:**
An enormous amount. The app now has: a real Node.js backend server with authentication, persistent JSON-file-based storage, a full CRUD trip-planning workflow across 5 research categories (Accommodation, Activities, Transport, Restaurants, Flights) all following the same Research→Shortlisted→Selected→Booked→Travel→Review status workflow, a Budget module with live actual-vs-estimate tracking, an Expenses logger, a Journal with real photo upload (from mobile camera/library) and HTML export, multi-trip support (create/archive/delete trips from a Landing page), multi-user login with per-item "added by" attribution, concurrency-safe (race-condition-free) writes for the highest-traffic data, a PWA (installable, works offline for cached content), and it is **actually deployed and live** on the user's own domain (`deploytelco.com.au`) via VentraIP cPanel hosting, connected to a GitHub repository for version control and deployment. **The app's current public URL is `www.deploytelco.com.au/TOS`** (changed from `/COMPASS-TOS` on 2026-08-08 — see the URL-change note in Section 13).

**Current state of completion:**
The core application is feature-complete and live/working. The team was in the middle of addressing a list of 10 user-reported issues/improvements found through actually using the tool (see Section 6). 6 of those 10 are done. Work stopped mid-way through the user asking "where do I edit the name of an existing day?" — **this is a confirmed real bug: there is currently NO way to edit an existing day's title after it's created.** This is the very next task. ### Assumptions made

### Constraints

- **No frameworks.** Plain HTML/CSS/vanilla JS on the frontend; plain Node.js (`http`, `fs`, `path` built-in modules only, **zero npm dependencies**) on the backend. This was an explicit, repeatedly-honored constraint from the original handover doc.

- The AI assistant (me, in this conversation) has **no direct access** to the user's live server or local machine — every fix has to be described as files to download + manual deployment steps for the user to carry out themselves via cPanel/Terminal/GitHub Desktop.
- The AI's own sandboxed bash environment has **no internet access** (network egress disabled) and does **not persist background processes between separate tool calls** — this caused repeated confusion early on (starting a test server in one command, then trying to curl it in a separate command, getting connection-refused). The fix was always to do setup + test in one single bash command.

### Definitions of important terms

- **COMPASS-TOS**: The application's name. "Travel Operating System."
- **Trip / Project**: A single planned trip, stored as a folder under `data/projects/<slug-id>/` containing ~15 JSON files. The app supports multiple trips (multi-tenancy at the folder level).
- **"Build N"**: The AI's own internal numbering for each logical batch of changes delivered in a message (e.g., "Build 25"). This numbering is informal/for tracking purposes only — it does NOT correspond to git commits 1:1, since the user often batched multiple "Builds" into a single git commit, or deployed builds out of order. **Do not assume build numbers are reliable version markers on the live server** — always verify via `grep`/`git log` on the actual server what's really deployed.
- **Atomic/concurrency-safe write**: A server-side operation that does a synchronous (no `await` in between) read-modify-write of a JSON file, exploiting Node's single-threaded event loop to guarantee no two simultaneous requests can interleave and lose data. This was built specifically to solve a real "two family members editing at once" data-loss risk.
- **`API_BASE`**: A browser-computed JavaScript global (`window.API_BASE`), calculated from `window.location.pathname`, representing the URL subfolder the app is currently running from (e.g., `/TOS` or empty string for domain root). Used to prefix every `fetch()` call to the backend API so the app works correctly regardless of what subfolder path it's deployed under.
- **`BASE_PATH`**: The server-side counterpart — an environment variable (`process.env.BASE_PATH`) telling `server.js` its own mount-point prefix, which it strips from every incoming request's URL before routing, since the LiteSpeed reverse proxy does NOT strip this prefix automatically (confirmed by direct testing — this was a wrong assumption initially, then corrected).
- **VentraIP**: The user's Australian domain registrar and web hosting provider. Domain: `deploytelco.com.au`. Hosting is cPanel-based, running on **LiteSpeed** web server (confirmed via `lsnode` processes seen in `ps aux` output and HTTP response headers), NOT Apache/Passenger as originally assumed.
- **Placeholder/generic data**: Deliberately fake trip data (e.g., "Sample Trip," "Destination A," "Traveller 1") used throughout for testing, per the user's explicit instruction to not treat any current data as real/precious.

## 3. Requirements

### Functional requirements

- Multi-trip support: create, list, open, archive, and permanently delete trips.
- Each trip has: a Journey (day-by-day itinerary), and five research categories — Accommodation, Activities, Transport, Restaurants, Flights — each following the same **Research → Shortlisted → Selected → Booked → Travel → Review** status workflow.
- A Budget module comparing planning estimates against live actual spend (calculated automatically from the research categories' prices).
- An Expenses module for logging real day-to-day spending.
- A Journal module: per-day notes, checklist, and photos (uploaded from camera/library, or linked externally), exportable as a single standalone HTML file at trip's end.
- A Destination Workspace: a per-place hub showing Accommodation/Activities/Restaurants/Transport/Weather/Journal content relevant to that destination across however many days are spent there.
- Multi-user logins (multiple username/password pairs), with automatic "Added by [name]" attribution on everything created.
- Trip dates: editable start date; day-by-day dates recalculate automatically, respecting flight arrival facts (so an overnight/date-line-crossing flight correctly shifts all subsequent days).
- Route planning: manual distance/duration/tolls entry (no paid routing API), plus "Open in Google Maps"/"Open in Waze" deep links (using coordinates if available, falling back to text addresses).
- Weather: seasonal averages (static JSON) plus an attempted live forecast via Open-Meteo (free, no API key) if the destination has saved coordinates.
- PWA: installable to home screen, works offline for previously-loaded content (via Service Worker with a stale-while-revalidate caching strategy for the app shell, network-first for trip data, network-only for API writes).

### Non-functional requirements

- **Real persistence.** Every user action must survive a server restart. (This was NOT true in early builds — a major fix was adding the actual backend/file-write layer.)
- **Concurrency safety** for the highest-collision-risk data (Journal photos/checklist, and all 5 research categories + Flights) — implemented via atomic server-side read-modify-write, tested under real simulated concurrent load (8-10 simultaneous requests, zero data loss confirmed).
- **Portability across deployment paths** — the app must work whether mounted at a domain's root or any subfolder, without code changes (only an environment variable). This was a real, hard-won fix (see Section 9).
- **Zero external runtime dependencies** on the backend (`npm install` should always complete instantly with nothing to download).
- Basic security: HTTP Basic Auth (not enterprise-grade, proportionate to a small family use case), server-side input validation on all write endpoints, path-traversal protection on file operations.

### Style or formatting requirements

- JavaScript style throughout the codebase: extremely vertically spaced (blank line between almost every statement) — this is the established house style across every single file in this project, copied faithfully in every new file the AI created. **Continue this style for consistency** — e.g.:

  ```js
  const x = 1;

  const y = 2;

  return x + y;
  ```

- CSS uses a warm, muted palette: navy `#243447`/`#34495E`, gold/tan `#C79C5D`, cream background `#F8F5F0`. Badge colors added for status: `.badge-selected` (amber `#fbe9d0`/`#8a5a18`), `.badge-booked` (green `#e1f0e3`/`#2e7d4f`).
- No inline `<style>` blocks were originally intended (per the old README's "HTML Standards" section — "No inline styling, Shared CSS") but in practice a large `<style>` block exists inside `index.html` itself (a pragmatic departure from the original stated ideal, never corrected — low priority to fix).

### Mandatory rules that must continue to be followed

From the explicit handover document the user provided mid-project (`COMPASS-TOS_Development_Handover.md`):

- **Evolve existing files instead of redesigning architecture.**
- **One feature per build** (informally relaxed over time as bug-fix batches grew, but still a good default).
- **Existing files take precedence over creating new ones.**
- **Deliver complete replacement files**, not diffs/patches, when giving code to the user.
- **JSON stores facts only** — never store calculated/derived values (e.g., day dates are calculated from the trip start date + flight facts, not manually re-entered; distance/duration for driving legs are facts the user enters from looking at Google Maps, not computed by the app).
- Every code change should ideally be tested before being handed to the user — this project developed a strong practice of the AI actually starting the real Node server in its sandbox and firing real HTTP requests (including deliberately concurrent ones) to prove fixes work, rather than just asserting they should work. **This practice should continue.**

## 4. Decisions Made

| Decision                                                                                                                            | Rationale                                                                                                                                                                                                                   | Alternatives rejected                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Plain Node.js backend, zero dependencies                                                                                            | Matches the project's explicit "no frameworks" principle; avoids `npm install` friction on shared hosting                                                                                                                   | Express.js (more ergonomic but violates the no-frameworks rule)                                                                                                                                        |
| JSON files on disk as the database (not a real DB)                                                                                  | Simple, matches "JSON stores facts" philosophy, human-readable/editable, no DB server to host                                                                                                                               | SQLite, MySQL, MongoDB Atlas — all considered but rejected as unnecessary complexity for a small family tool                                                                                           |
| Basic Auth for multi-user login, not a full session/login system                                                                    | Proportionate security for a small trusted family group; simple to implement in a framework-free server                                                                                                                     | Cookie-based sessions with hashed passwords — more "correct" but much more code for little practical benefit here                                                                                      |
| Server-generates all record IDs (timestamp+random), not client-side "scan for max+1"                                                | Client-side ID generation has its own race condition under concurrent adds; server-side is provably collision-free                                                                                                          | Sequential padded IDs (ACC-0001 style) — abandoned in favor of `PREFIX-timestamp-random`                                                                                                               |
| Atomic read-modify-write via synchronous fs calls (no `await` between read and write)                                               | Node's single-threaded event loop guarantees no interleaving for purely synchronous code — genuinely safe with no external locking library needed                                                                           | An explicit mutex/lock library, a job queue — both rejected as unnecessary given the synchronous-fs-call trick works and needs zero dependencies                                                       |
| Frankfurter (ECB rates) instead of Wise API for currency conversion (planned, not yet built)                                        | Wise has no genuinely free/public no-signup exchange rate endpoint (confirmed via web search) — would require a business account. Frankfurter is genuinely free, no key, and uses the same "mid-market rate" concept        | An unofficial third-party Wise-scraping wrapper API — explicitly rejected as too unreliable/untrustworthy for a tool used while actually traveling                                                     |
| Google Maps/Waze via deep links, not a live routing API                                                                             | No paid Google Maps Platform account set up; deep links need zero backend/API key and hand off to real apps for live routing                                                                                                | Google Routes API (would give real tolls data but needs a billing account); Radar.com (evaluated — good distance/duration but no toll-cost data, and unclear self-serve free tier as of research date) |
| Making the legacy Italy-specific repo content fully generic/placeholder                                                             | Explicit user instruction — treat nothing currently in the app as real/precious data                                                                                                                                        | Leaving the original Italy content in place — rejected per direct user instruction                                                                                                                     |
| PWA service worker: stale-while-revalidate for app shell, not pure cache-first                                                      | Pure cache-first meant updates NEVER reached returning visitors (a real bug that was found and fixed) — stale-while-revalidate still serves instantly from cache but always refreshes in the background                     | Pure cache-first (original, buggy approach); network-first for everything (would break offline support)                                                                                                |
| `API_BASE` (client) + `BASE_PATH` (server env var) for portable deployment paths                                                    | Confirmed via direct testing that the LiteSpeed proxy does NOT strip the subfolder prefix before forwarding to Node — so both the browser's outgoing requests AND the server's own routing needed to become subfolder-aware | Assuming the proxy strips the prefix (this was tried first, based on reasoning about how "these things usually work," and was **proven wrong** by an actual 404 test)                                  |
| Flights rebuilt as its own full research module (own `flights.json`, day-keyed) rather than staying embedded in `journey.json`      | User explicitly requested full Research→Booked workflow for flights, matching other categories; embedding in journey.json never supported that                                                                              | Keeping flights as lightweight facts inside journey.json (the original, more limited design)                                                                                                           |
| Planner's day-item status badges pull LIVE data from the real research collections, not the static `journey.json` placeholder items | Discovered mid-project that the old display was completely disconnected from real data — selecting/booking something never updated what the Planner showed. This was a real bug, not a stylistic choice                     | Leaving the static placeholder display and just recoloring it (rejected once the disconnect was discovered — would have shipped a cosmetic fix over a real bug)                                        |

## 9. Known Issues

### Bugs (confirmed, currently unfixed)

- **Day title cannot be edited after creation.** (Section 6/8 — the active task.)

### Bugs (found and FIXED during this project — listed here so the next AI doesn't need to rediscover them, but should stay alert for similar patterns elsewhere)

- Dashboard was 100% hardcoded to the original Italy trip's data (name, dates, budget figure, progress text, countdown target) — fixed, now reads live `Project.get("project")` data.
- Planner's per-day item status was reading from stale, disconnected `journey.json` static placeholder items instead of live research-module data — fixed.
- Budget's `calculateActual()` summed every item's price regardless of status, even bare "Research" ideas — fixed to filter to Shortlisted-and-beyond.
- `weather.json` missing from new-trip generation — fixed.
- Service worker used pure cache-first, meaning app updates never reached returning visitors — fixed to stale-while-revalidate; also needed an HTTP `Cache-Control: no-cache` header specifically on `index.html` and `service-worker.js` to close a second layer of the same staleness problem.
- A `req.url === "/api/projects"` strict-equality route check (inconsistent with every other route's tolerant regex pattern) caused a real, hard-to-diagnose 404 in production when the URL had a trailing slash or query string appended by the reverse proxy — fixed to match the tolerant pattern used elsewhere.
- Multiple absolute (`/api/...`, `/service-worker.js`) paths broke when the app was moved to a subfolder deployment — fixed via `API_BASE` (client) + `BASE_PATH` (server env var) + relative paths in the service worker's own file list.

### Risks / architectural notes for the next AI

- **The AI's sandboxed bash environment does not persist background processes between separate tool calls.** Any test that starts `node server.js` in the background MUST do all its `curl`/testing in the exact same bash command, or the server process will be gone and every request will get connection-refused. This tripped up the AI multiple times during this project — don't repeat it.
- **The AI's sandbox has no internet access.** Cannot verify external APIs (Open-Meteo, Frankfurter, Google Maps) actually work from within the sandbox — can only verify the request-construction logic is correct, and must be honest with the user that live external calls need to be verified in their actual browser.
- **Deployment is entirely manual and error-prone.** The user copies files into a local Git-tracked folder (via GitHub Desktop), pushes to GitHub, then on the actual server runs `git pull origin master` via Terminal (cPanel's own "Update from Remote" Git UI button proved unreliable and was abandoned in favor of direct terminal `git pull`), then must manually find and `kill -9` the old Node process PIDs (cPanel's own Restart/Stop-Start buttons in "Setup Node.js App" did NOT reliably cycle the process — this was confirmed multiple times) before clicking Start again. **This exact sequence should be given to the user for every deployment**, since simpler approaches (just clicking Restart) have repeatedly failed to actually apply new code.
- **File-location mistakes are common and hard to self-diagnose.** At least twice, a file was accidentally placed in the wrong folder (`app/server.js` instead of repo root; a case-mismatched `Projects` vs `projects` folder). The most reliable diagnostic tool proved to be `git show --stat HEAD` on the server (shows exactly which files a commit touched and where) combined with direct `grep`/`cat` checks of the actual deployed file content — **prefer these over asking the user to describe symptoms when a deployment seems not to have taken effect.**
- **cPanel/LiteSpeed's Node app hosting can silently reassign an app's URL mount point** when a second Node app is added to the same account — this already happened once and caused a major outage. If the user ever adds more Node apps to this hosting account, proactively check whether COMPASS-TOS's Application URL setting has changed.
- **Do not assume the LiteSpeed reverse proxy strips a subfolder mount prefix before forwarding to Node** — it does NOT, confirmed by direct testing. If this app (or any future app on this same hosting) is ever moved between root and a subfolder again, both `API_BASE` (client) and `BASE_PATH` (server env var) need to be correctly set/left correctly for it to keep working.
- **`git log -1` / `grep` on the live server is the most reliable way to verify what's actually deployed** — the user's own description of symptoms, or even cPanel's UI (e.g., "started" status), can be misleading (a process can show "started" while still running old code if the restart didn't actually cycle it).

### Missing information / open questions

- Whether the user wants Frankfurter or is willing to set up a real Wise Business API account for currency conversion (item #4) — **needs to be asked**, not assumed.
- Exact scope of item #9 (calendar opens to date) — which calendar/date field, in which part of the UI — **needs to be asked**.

## 10. Important Context the Next AI Must Preserve

### User preferences

- Wants thorough, real testing before being told something works — this AI adopted a strong practice of actually running the Node server and firing real HTTP requests (including concurrent-load tests) rather than just asserting correctness, and the user has come to expect this level of rigor. **Continue this.**
- Prefers being walked through deployment steps explicitly and numbered, since cPanel/Terminal/GitHub Desktop are not native territory for them even though they're capable of executing instructions precisely.
- Appreciates being told plainly when something is a bug vs. a deployment issue vs. a misunderstanding, rather than vague reassurance.
- Explicitly stated placeholder data should be treated as disposable/replaceable, not precious — don't be overly cautious about modifying test data.
- Wants family-friendly, low-friction multi-user access (shared logins are fine, no complex permissions system wanted — user explicitly said "everyone has equal full access, just under their own name" when asked).

### Writing style

- The AI's own communication style throughout this project: concise, confident, technical-but-plain-English explanations, clear numbered deployment steps, honest about uncertainty (e.g., clearly distinguishing "I tested this directly" from "I can't test this in my sandbox, please verify"), minimal fluff/preamble, leads with the actual finding/fix rather than restating the question.

### Naming conventions

- Trip folder IDs: lowercase-hyphenated slugs (e.g., `la-grande-italia-2027`, `sample-trip-two`).
- Item ID prefixes: `ACC-` (accommodation), `ACT-` (activities), `TRN-` (transport), `RST-` (restaurants), `EXP-` (expenses), `FLT-` (flights), `CHK-` (journal checklist), `PHT-` (journal photo) — all followed by `-<timestamp>-<random6chars>`.
- Status workflow values (exact strings, case-sensitive): `"Research"`, `"Shortlisted"`, `"Selected"`, `"Booked"`, `"Travel"`, `"Review"`.
- Destination "slugs" used as identifiers: lowercase-hyphenated (e.g., `destination-a`).

### Terminology

- See Section 2's Definitions. Key ones to not confuse: "Build N" (informal AI tracking, not a real version) vs. actual git commits; `API_BASE` (client) vs. `BASE_PATH` (server) — easy to mix up, they solve the same class of problem from opposite ends.

### Recurring instructions

- "Send server.js again" / "resend X" — the user has occasionally needed files re-sent due to confusion about which version they had locally across a long multi-file conversation. Always regenerate from the AI's own current working copy (the sandbox `/home/claude/build/repo/` — or wherever the next AI's equivalent working copy lives) rather than trusting an old copy-paste, to guarantee correctness.
- Deployment steps should always be given as a clear, numbered sequence ending in the kill-PID-then-Start restart cycle, not just "restart the app."

### Things to avoid

- Don't invent CSS variable names that aren't actually defined in `assets/css/themes/light.css` (`--color-bg`, `--color-primary`, `--color-secondary`, `--color-text`, `--radius` are the only ones that exist).
- Don't assume a mockup/visualization tool's design system matches the real app's actual CSS — verify against the real stylesheet before writing production code based on a mockup.
- Don't assume LiteSpeed/cPanel proxy behavior without testing — assumptions about "how these things usually work" were wrong at least once and caused real debugging time.
- Don't trust cPanel's "started" status or Restart button alone as proof that new code is live — always independently verify via `grep`/`git log` on the actual server.
- Don't test a background server process across separate bash tool calls — always test within the same call it was started in.
- Don't build features assuming external APIs work without flagging that live external calls can't be verified from the sandbox.
